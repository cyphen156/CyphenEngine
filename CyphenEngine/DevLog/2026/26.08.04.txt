작업 요약
	#4_14에서 확정한 혼합 Object 계층의 Runtime 소속 전파를 실제 UpdateFunction 등록과 실행 그룹까지 확장했습니다.

	GameRuntime마다 UpdateManager 하나를 소유하고, 같은 실행 함수 포인터를 사용하는 Object target을 Function Group으로 묶어 Runtime-global 및 World-local 실행 목록을 관리하도록 구성했습니다.

	GameObject는 자신과 직접 Component의 실행 함수를 공급하고 GameRuntime은 현재 Runtime과 가장 가까운 WorldObject anchor를 기준으로 등록 위치를 결정하도록 책임을 분리했습니다.

	Attach, Detach, Leave와 파괴 경로에서 Runtime, World 및 실행 참여가 각 객체 종류의 독립 가능성에 맞게 정리되도록 생명주기 계약을 개정했습니다.

	Runtime 1개, World 3개와 Object 10,000개를 사용하는 부하 구성을 만들고 세 계열의 16가지 UpdateParticipation 조합을 실제 첫 Tick에서 검증했습니다.


진행한 커밋
	#4_15 [Update:Runtime] 계층형 Update 참여와 함수 그룹 관리 구성


문제 정의
	#4_13의 UpdateFunction은 Object 포인터와 실행 함수 포인터를 한 쌍으로 저장했습니다.

	같은 클래스의 여러 인스턴스가 동일한 실행 함수를 사용하더라도 각 원소가 같은 함수 포인터를 반복 보유했고, GameRuntime과 World가 자신의 실행 목록과 등록 및 해제 규칙을 각각 직접 관리했습니다.

	#4_14에서는 혼합 Object 계층에 포함된 모든 GameObject의 Runtime 소속을 평면 장부에 연결했지만, 하위 GameObject와 Component의 네 UpdateParticipation 단계를 어느 실행 그룹에 등록하고 관계 변경 시 어떻게 제거할지는 남아 있었습니다.

	일반 GameObject의 World-local 실행 문맥은 자신의 필드가 아니라 가장 가까운 WorldObject anchor에서 파생됩니다. Component는 독립적인 Runtime과 World 문맥을 갖지 않으므로 직접 부모 GameObject가 실행 참여를 대행해야 합니다.

	따라서 실행 함수 그룹의 소유자, 구체 타입의 함수 주소를 봉인하는 시점, Component의 공급 책임과 Detach 및 파괴 시 대칭 해제를 하나의 계약으로 정리해야 했습니다.


주요 설계 결정
	1. Runtime별 UpdateManager 소유
		UpdateManager는 전역 singleton이나 World별 객체가 아니라 GameRuntime마다 하나씩 소유합니다.

		World는 항상 하나의 Runtime에 종속되고 World-local Update와 FinalUpdate도 해당 Runtime의 실행 세계선에 포함되므로, Runtime 하나가 자신의 Global 그룹과 모든 World별 그룹을 함께 관리하는 것이 자연스럽습니다.

		UpdateManager는 GameRuntime 타입을 알지 않으며 실행도 담당하지 않습니다. 등록과 해제, 같은 execute 함수의 target 그룹화와 World별 실행 목록 수명만 관리합니다.

		GameRuntime과 World는 UpdateManager가 제공한 읽기 전용 Function Group을 각자의 Tick 단계에서 직접 순회합니다.

	2. UpdateFunction과 Function Group의 역할 분리
		UpdateFunction은 Object 포인터와 UpdateExecuteFunction 포인터를 보유하는 POD 전달값입니다.

		등록과 해제 시 필요한 단일 실행 단계의 UpdateFunction만 임시로 생성하여 UpdateManager에 전달하고 객체가 통합 binding 구조체를 영구 보유하지 않도록 했습니다.

		UpdateFunctionGroup은 같은 execute를 사용하는 Object target 목록을 보유합니다. 함수 포인터를 그룹당 한 번만 저장하고 target 배열을 평면 순회하여 반복 저장 비용과 실행 목록의 원소 크기를 줄였습니다.

		Runtime-global의 GlobalUpdate와 GlobalFinalUpdate는 서로 독립된 그룹 목록으로 관리합니다. World-local의 Update와 FinalUpdate도 World마다 독립된 그룹 목록을 사용해 같은 함수가 여러 World의 서로 다른 인스턴스를 분리하여 실행할 수 있도록 했습니다.

	3. 구체 타입 실행 함수 봉인
		GameObject와 Component는 요청받은 단일 UpdateParticipation 단계의 UpdateFunction을 생성하는 virtual 계약을 제공합니다.

		MakeUpdateFunction은 실제 파생 타입과 해당 타입의 virtual Update 진입점을 ExecuteUpdateFunction 템플릿에 봉인합니다.

		실행 시 UpdateManager, GameRuntime과 World는 GameObject, Component 또는 사용자 파생 타입을 판별하지 않습니다. 저장된 thunk가 Object 포인터를 등록 당시 타입으로 복구한 뒤 virtual 함수를 호출합니다.

		테스트 파생 타입도 CreateUpdateFunction을 직접 구현하여 TestRuntimeObject, TestWorldObject와 TestComponent 각각의 구체 타입이 thunk에 반영되는지 확인했습니다.

	4. GameObject의 Component 공급 책임
		Component는 GameRuntime과 UpdateManager를 직접 알지 않습니다.

		GameObject::GetUpdateFunctions는 요청받은 한 실행 단계에 대해 GameObject 자신과 직접 부착된 Component 중 참여를 선언한 대상의 임시 UpdateFunction 목록을 공급합니다.

		GameRuntime은 전달받은 목록을 Runtime-global 또는 World-local 그룹에 등록하거나 해제합니다. 등록 위치를 판단하는 책임과 구체 실행 함수를 만드는 책임을 분리했습니다.

		Component Attach와 Detach는 직접 부모 GameObject가 실행 참여 등록과 해제를 대행합니다. Component 아래의 GameObject는 Component가 독립 실행 루트가 될 수 없다는 규칙에 따라 Component와 함께 Runtime 실행 문맥에서 제거됩니다.

	5. Runtime 및 World 실행 문맥
		GameRuntime::Admit은 전달받은 GameObject의 혼합 Object 서브트리를 부모 우선으로 순회합니다.

		각 GameObject의 Runtime 소속을 평면 장부에 추가하고 해당 객체와 직접 Component의 네 실행 단계를 하나씩 공급받아 등록합니다. 중간 단계가 실패하면 이번 Admit에서 추가한 접미부를 역순으로 해제하여 Runtime 소속과 실행 장부를 호출 이전 상태로 되돌립니다.

		GlobalUpdate와 GlobalFinalUpdate는 Runtime-global 그룹에 등록합니다.

		Update와 FinalUpdate는 현재 GameObject부터 Outer 방향으로 탐색한 최초의 WorldObject를 anchor로 사용합니다. 해당 WorldObject가 World에 참여하지 않았다면 World-local 실행 그룹에는 등록하지 않으며 더 위의 WorldObject를 대신 사용하지 않습니다.

		중첩 WorldObject는 같은 Runtime 안에서 서로 다른 World에 참여할 수 있고 각자 자신의 서브트리에 독립적인 World 실행 경계를 형성합니다.

	6. Detach, Leave와 파괴 계약
		일반 GameObject를 Detach하면 Runtime 소속과 Runtime-global 실행 참여는 유지하지만 기존 Outer에서 파생된 World-local Update와 FinalUpdate 참여는 제거합니다.

		WorldObject를 Detach하면 스스로 독립적인 World anchor가 될 수 있으므로 기존 World와 Runtime 및 네 실행 참여를 유지합니다.

		Component를 Detach하면 Component 자신과 그 아래 GameObject는 독립 실행 구성을 유지할 수 없으므로 실행 그룹과 Runtime에서 탈퇴합니다.

		GameRuntime::Leave는 서브트리에 포함된 WorldObject를 World에서 먼저 탈퇴시키고 모든 GameObject의 실행 참여와 Runtime 소속을 함께 제거합니다.

		ObjectManager의 공통 파괴 경로는 자식 파괴, 현재 객체의 OnDestroy, 부모 Detach와 Registry 제거 순서를 사용합니다. 실제 메모리 수집 전에 Runtime, World와 실행 장부 관계를 정리하도록 기존 파생 Destroy 책임을 OnDestroy 계약으로 통합했습니다.

	7. Scheduler와 활성 상태의 현재 경계
		Scheduler는 Execution Priority 계약을 추가할 위치만 확보하고 실제 우선순위 정렬은 구현하지 않았습니다.

		기존 IsActive 분기를 실행 thunk에서 제거했습니다. 객체 활성 상태는 후속 ActivationPivot이 각 Function Group의 active 구간을 관리할 때 다시 연결하며, 현재 구현이 활성 제어를 제공하는 것처럼 보이지 않도록 했습니다.


RuntimeTest 개정
	1. 모든 UpdateParticipation 조합 구성
		TestRuntimeObject, TestWorldObject와 TestComponent에 None부터 네 단계 전체 참여까지 16가지 조합의 최종 파생 타입을 각각 구성했습니다.

		각 타입은 생성자에서 참여 조합을 고정하고 네 virtual Update 호출 횟수를 인스턴스별 TestUpdateCallCounts에 기록합니다.

		첫 Runtime Tick 이후 세 계열의 16가지 조합, 총 48개 대표 인스턴스가 선언한 단계만 정확히 한 번 실행했는지 확인했습니다.

	2. 혼합 서브트리 경로 검증
		일반 Object와 Component를 통과하는 중첩 GameObject 경로의 Runtime 참여와 Component Detach 이후 하위 Runtime 탈퇴를 확인했습니다.

		Component 아래에서 독립적으로 Runtime에 참여하려는 GameObject를 거부하는지 검증했습니다.

		중첩 WorldObject가 같은 Runtime의 다른 World에 참여하고 서로 독립적인 World anchor를 유지하는지 확인했습니다.

		World에 참여한 WorldObject를 구조적으로 Detach해도 World anchor와 Runtime 소속을 유지하는지 확인했습니다.

		GameRuntime::Leave가 WorldObject의 World와 Runtime 소속을 함께 제거하는지 확인했습니다.

	3. 최종 부하 구성
		GameRuntime 1개가 World 3개를 소유하도록 구성했습니다.

		WorldObject 2,500개, 일반 GameObject 2,500개, Component 2,500개와 일반 Object 2,500개를 생성하여 총 10,000개 Object를 유지했습니다.

		2,498개 WorldObject cluster를 세 World에 순환 배치하고 각 cluster에 Object bridge, 중첩 GameObject와 Component를 구성했습니다.

		16가지 UpdateParticipation 조합을 모든 계열에 반복 배치하여 한 프레임에 약 15,000회의 virtual Update 호출이 발생하도록 구성했습니다.

남은 논의
	1. Execution Priority와 Scheduler
		객체 또는 함수 그룹 단위의 우선순위 계약이 확정되면 UpdateManager가 소유한 그룹 목록을 Scheduler에 전달하여 실행 순서를 재구성합니다.

	2. ActivationPivot
		Function Group 안에서 활성 target과 비활성 target을 분할하고 SetActive가 각 참여 그룹의 pivot을 이동시키는 관리 경계를 설계합니다.

	3. 실행 중 변경 안전 지점
		UpdateFunction Group 순회 중 Attach, Detach, Leave 또는 Destroy가 발생해 vector와 Object 수명이 변경되는 문제는 이벤트 시스템 작업에서 ObjectHandle 기반 지연 처리와 고정된 동기화 지점으로 다룹니다.
