작업 요약
	#4_15에서 마감한 Runtime 실행 참여 위에 실제 2D 월드 표시 경로를 얹기 위해 #4_16의 작업 범위를 정리했습니다.

	이번 커밋에서는 소스 배치 규약을 <계층>/<도메인>/{Public,Private}로 정리하고 Core Math를 그 규약의 첫 적용 대상으로 옮겼습니다.

	표현과 시점 타입의 구성, World 상태를 tick 시점에 고정해 Renderer로 전달하는 경계는 방향까지만 정리했고 구현은 다음 작업으로 미뤘습니다.


진행한 커밋
	#4_16 [Refactor:Core] Math 소스 배치를 계층-도메인 폴더 규약으로 정리


문제 정의
	현재 엔진 루프는 World에 살아 있는 객체를 읽지 않습니다.

	RuntimeTest가 -0.5와 0.5 위치에 Square 두 개와 서로 다른 ResourceId의 Sprite를 유지하지만, Frame에는 프레임 번호로 고른 debug ResourceId 하나만 실립니다.

	TexturedQuadDrawItem과 DrawTexturedQuadCommand에는 textureId만 있고 위치 정보가 없습니다. 화면에 나오는 것은 World 표시가 아니라 여전히 debug bootstrap 표시입니다.

	즉 World 안의 인스턴스를 특정 시점의 값으로 고정해 렌더 입력으로 확정하는 단계가 통째로 비어 있습니다.

	여기에 더해 Core Math가 Core/Public 아래 평면으로 놓여 있어 계층 공개 경계와 도메인 경계가 한 폴더에 섞여 있었습니다. 내장 표현 타입과 시점 타입이 추가되면 같은 문제가 Runtime에서 반복될 상황이었습니다.


주요 정리 내용
	1. 소스 배치 규약
		소스 배치를 <계층>/<도메인>/{Public,Private} 형태로 정리했습니다.

		계층의 기반 계약은 계층 Public에 두고, 그 위에 얹히는 확장 타입은 도메인 폴더에서 관리합니다.

		Core Math를 첫 적용 대상으로 Core/Public/Math에서 Core/Math/Public으로 옮겼습니다. 이동한 헤더의 변경은 상호 include 경로뿐이며 타입과 연산 구현은 바뀌지 않았습니다.

	2. 실행 계층별 책임 경계
		Runtime은 무엇이 존재하고 그것이 무슨 의미인지를 소유합니다.

		Renderer는 그 의미를 이번 화면에서 어떤 방식으로 그릴지 결정합니다. 시점 선택, 가시성 판정, 정렬, 표현 방식 선택과 RenderCommand 생성이 여기에 속합니다.

		Backend는 command만 실행하며 의미를 알지 않습니다.

		Object는 어떤 컴포넌트를 구성하는지로 자신이 무엇으로 표현되는지를 정의하며, 어떻게 그려지는지는 정의하지 않습니다.

	3. tick 고정 상태와 Frame
		Frame은 특정 simulation tick에 고정된 불변 상태입니다. 고정한 뒤에는 live World가 변해도 Frame이 변하지 않습니다.

		렌더 목적 캡처는 렌더 소비자가 있는 데이터만 채웁니다. 물리 상태처럼 렌더 소비자가 없는 데이터는 담지 않으며, 물리 결과는 이미 Transform으로 표현됩니다.

		이 캡처는 복원 가능성을 주장하지 않습니다. 복원 목적 캡처가 필요해지면 같은 기록 포맷에 다른 채움 범위와 보관 정책으로 별도 정의합니다.

		전체 상태를 매번 전달하므로 프레임이 유실되어도 다음 캡처 하나로 상태가 복구됩니다. 변경분만 전달하는 방식과 달리 렌더 측 표현이 영구히 어긋나지 않습니다.

	4. 표현 대상과 가시 대상의 구분
		표현 컴포넌트를 가졌는지는 스키마 사실이며 Runtime이 압니다.

		이번 프레임에 실제로 보이는지는 시점과의 교차 결과이며 Renderer만 판단합니다.

		Runtime은 표현 대상과 시점이라는 두 입력을 공급하고, 두 입력의 교집합 계산은 Renderer가 수행합니다.

	5. 카메라의 위치
		카메라는 Renderer의 설정값이 아니라 World에 존재하는 대상입니다. 시점식 데이터는 표현식 데이터와 같은 격의 논리 의미입니다.

		활성 시점 선택은 게임 로직의 결정이므로 월드 상태입니다. Renderer는 공급받은 활성 시점을 사용합니다.

		카메라는 하나로 제한하지 않습니다. 활성 시점이 여럿이면 Renderer가 그 수만큼 뷰 패스를 구성합니다. Runtime과 World 상태를 전역으로 두지 않는다는 기존 결정과 같은 이유입니다.

		화면 상하 좌우 반전은 카메라가 아니라 Renderer seam에서 다룹니다.

	6. 변경분 추적의 위치
		변경분 추적은 캡처 전송량을 줄이지 않습니다. 전체 상태를 이미 전달하므로 전송 비용은 그대로입니다.

		변경분 추적이 줄이는 것은 커맨드 캐시 재구성, GPU 상주 버퍼 업로드, 정렬 구조 갱신 같은 하류 작업입니다. 따라서 그 판단과 이전 상태 보관은 Renderer 쪽에 둡니다.

		현재는 측정 근거가 없으므로 도입하지 않습니다. 매 프레임 전체 캡처를 유지하되 재사용 대상은 이전 프레임의 데이터가 아니라 버퍼로 둡니다.


정리된 설계 기준
	소스 배치는 <계층>/<도메인>/{Public,Private}를 따르고 기반 계약은 계층 Public에 남긴다.

	Runtime은 논리 상태를, Renderer는 표현 방식을, Backend는 실행만 소유한다.

	World는 Render Frame을 만들지 않는다. 자신의 논리 상태를 값으로 고정하는 책임만 가진다.

	Frame은 특정 tick에 고정된 불변 상태이며, 렌더 목적 캡처의 범위는 렌더 소비자가 있는 데이터로 한정한다.

	렌더 목적 캡처는 복원 가능성을 주장하지 않는다.

	표현 대상 여부는 스키마 사실이고 가시 여부는 렌더 판정이다.

	카메라는 월드 대상이며 복수를 허용한다.

	실행 중 RTTI와 타입 분기를 쓰지 않는다는 #4_15의 기준을 캡처 경로에도 동일하게 적용한다.


남은 결정
	1. 표현식 데이터의 소유 위치
		Sprite의 표현식 데이터를 OOP 컴포넌트에 둘지 World의 ComponentDataStorage에 둘지 확정하지 않았습니다.

		캡처가 매 프레임 표현 대상을 열거해야 하므로, 객체 트리를 타입 판별로 훑지 않는 열거 경로가 함께 필요합니다. 현재 ComponentDataStorage에는 순회 경계가 없습니다.

	2. 컴포넌트의 상대 Transform
		컴포넌트가 소유 객체 기준 상대 Transform을 갖는 것은 금지된 바 없습니다. World storage의 SSOT 규칙은 World에 Join한 WorldObject의 Transform을 대상으로 합니다.

		도입하면 계층 합성 규칙이 함께 필요하며, 합성은 공간 논리이므로 주체는 Runtime입니다.

	3. 내장 타입 구성
		SpriteComponent와 CameraComponent의 필드와 계약을 확정하지 않았습니다.

		편의 객체를 정식으로 둘지, 둔다면 필수 컴포넌트 구성을 어느 경로에서 보장할지 남아 있습니다. 생성자는 실패를 반환할 수 없으므로 생성 후 초기화 훅과 Spawn 단계 합성 중 하나를 선택해야 합니다.

	4. 뷰 규약
		카메라의 투영 파라미터 집합이 곧 미뤄 둔 뷰 규약입니다. 필드를 정하는 시점에 원점의 화면 위치와 단위 대응이 함께 확정됩니다.

	5. Frame 전달 구조
		현재 Renderer는 pending frame 슬롯 하나를 mutex 아래 값 복사로 채웁니다. 전체 상태를 나르는 구조에서는 이 지점이 병목이 되므로 버퍼 교대 방식을 검토해야 합니다.

	6. 문서 정합
		Decisions.txt의 Live World / Snapshot / Render Frame 항목은 Frame을 표현 전용 입력으로, WorldSnapshot을 복구용 값 데이터로 읽히게 서술되어 있습니다.

		실제 의도는 특정 tick 상태를 불변 값으로 고정하는 것이 핵심이고 복원은 그 데이터가 열어 두는 후속 활용입니다. 문면을 그대로 두면 같은 오독이 반복되므로 정정이 필요합니다.
