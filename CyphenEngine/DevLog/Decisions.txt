CyphenEngine_World_Rule

	1. 월드 좌표계 축 방향
		왼손좌표계를 사용한다.
		X축의 양수 방향은 오른쪽이다.
		Y축의 양수 방향은 위쪽이다.
		Z축의 양수 방향은 화면 안쪽이자 월드의 앞쪽이다.

	2. 월드 공간
		무한 연속 평면이며 고정 경계를 두지 않는다.
		원점 (0, 0, 0)은 공간의 정준 기준점이다. (모니터 상 위치는 뷰/카메라 결정으로 미룬다)
		기본 단위는 1 unit = 1 meter로 한다.

	3. 연산 모델 (#4 2D 월드)
		#4의 월드 시뮬레이션(이동·충돌·질의)은 XY 평면으로 제약해 2차원으로 연산한다.
		Z는 #4에서 월드 연산 축이 아니라 깊이/레이어/정렬 값이며 렌더러가 사용한다.

	4. 좌표 공간 분리
		스크린/픽셀 공간은 월드 공간과 별개이며 뷰포트/투영 경계에서 변환한다.
		Core Math 값 타입은 원점 위치와 화면 flip에 중립이다.

	5. 저장 타입 (3D-ready)
		로드맵상 #5가 3D 확장이므로 저장 타입은 처음부터 3D-ready로 둔다.
		위치는 Vector(3D), 회전은 Quaternion, 객체 변환은 Transform(TRS)로 표현한다.
		#4는 평면 제약(z 고정, Z축 회전)으로 사용하며 Transform::FromPlanar가 그 제약을 표현한다.
		#5의 3D 확장은 이 평면 제약을 해제하는 것이다.
		진짜 2D 개념(UI/스크린/UV)은 Vector2를 쓴다.
	

CyphenEngine_World_Loop_Rule

*향후 구현 / 계획 변경에 따라 일부 또는 전체 개정될 수 있습니다.*
*네이밍은 임시로 두었으며, 구현 시점에 맞게 변경될 수 있습니다.*

	1. 기본 방향
		CyphenEngine World는 순수 ECS를 기본 모델로 삼지 않는다.
		OOP Object/Component를 기본 정의·저작 표면으로 둔다.
		다수·균일·hot-path 행동만 런타임에 System으로 enroll해 DOD 방식으로 실행한다.
		DOD는 정의 계층이 아니라 런타임 enroll 계층으로만 존재한다.
		이로써 순수 ECS의 시스템 증식과 엄격한 전역 순서를 피하고, 일회성 행동의 롱테일은 OOP에 남긴다.
		ObjectHandle과 EntityHandle은 독립된 관리 도메인의 정체성이다.
		두 Handle의 내부 값이 같더라도 같은 대상을 의미하지 않으며, 관계가 필요하면 명시적으로 연결한다.

	2. 두 실행 체계의 병존
		World에는 Object System과 Enrolled System이 병존한다.
		Object System은 OOP식 정의, 즉시 반영, 유니크 행동, 소수 객체 행동을 담당한다.
		Enrolled System은 RuntimeEntry / ComponentDataStorage 기반으로 다수·균일·hot-path 행동을 일괄 처리한다.
		Object System은 즉시성을 기대하는 영역이므로 기본적으로 병렬 compute graph에 넣지 않는다.
		Enrolled System은 안정된 입력을 기준으로 compute하고, 결과는 정해진 apply point에서만 World에 반영한다.
		World 소속, Object 종속 수명과 Update/System 실행 참여는 서로 다른 관계다.
		World에 Join했다고 Update 또는 System 참여가 자동으로 결정되지는 않는다.

	3. System (실행 단위)
		런타임 처리 단위의 정식 명칭은 System이다.
		Skul: Dimension Rift의 SubSystem은 사용자 정의 최적화 시스템 용어였으며, CyphenEngine에서는 Gameplay 계층에서 같은 사용성을 제공한다.
		Engine Core는 사용자 System을 직접 하드코딩하지 않고 Register / Enroll / Unenroll / Tick Phase 계약만 제공한다.
		Gameplay 계층은 System의 구성·등록·정책(어떤 Object를 어떤 RuntimeEntry로 묶을지)을 정의하되, compute 커널은 concrete/native로 유지한다. (스크립트 VM이 도입되어도 hot 루프는 스크립트로 실행하지 않는다)
		행동의 주체는 Object가 아니라 System이며, System은 자신의 RuntimeEntry 배열 또는 바인딩된 ComponentDataStorage 범위를 순회한다.
		System 수명 계약(Initialize / Tick / Shutdown)은 concrete 등록으로 구성하며 vtable/interface에 의존하지 않는다.
		추상은 System 경계(프레임당 1회 호출)에만 두고, hot 루프 내부는 concrete/monomorphic로 유지한다.

	4. DOD 적용 조건
		System(DOD)로 뽑는 기준은 다수·균일·hot-path이며, 개별 판정 공정성이 불필요하거나 명시 규칙으로 해결 가능한 경우다.
		소수·유니크·관계형(계층·공간 질의) 로직은 OOP 소유 또는 스크립트로 남긴다.
		적용 여부는 호출 횟수가 아니라 위 조건을 만족하는지로 판단한다.

	5. Enroll / Register / Unenroll
		아래 계약은 System 참여를 구현할 때 적용할 설계 기준이며 현재 #4_10 코드에는 아직 실행 Scheduler가 없다.
		Enroll은 System 참여를 확정하는 단일 구조 변경 프리미티브이며 안전 지점에서만 수행한다.
		진입 트리거는 둘이다: authoring-time 직접 Enroll, runtime Register 요청.
		Register는 Enroll의 대안이 아니라, 런타임에서 Enroll을 요청하는 지연 트리거다.
		Register는 즉시 System storage를 변경하지 않고 pending queue에 기록되며, 안전 지점에서 Enroll로 확정된다.
		이탈도 대칭이다. Unregister / 사망 / 범위 이탈은 pending 요청으로 기록되고, 안전 지점에서 Unenroll로 확정된다.
		RuntimeEntry가 SSOT이던 hot data는 Unenroll 전에 필요한 경우 World storage 또는 OOP Object로 write-back / hand-back한다.

	6. SSOT (단일 진실)
		Enroll / Register는 구조 변경 타이밍을 다루는 규칙이며, 데이터 소유 문제를 해결하지 않는다.
		데이터 소유와 stale 방지는 SSOT 규칙이 담당한다.
		현재 구현에서 World에 Join한 WorldObject의 Transform은 World의 ComponentDataStorage가 유일한 SSOT다.
		Sprite와 이후 ComponentData의 소유 위치는 실제 System 소비 경로가 생길 때 별도로 결정한다.
		System이 단독 소유하고 다른 System/Object가 읽지 않는 hot data만 RuntimeEntry에 인라인으로 둘 수 있다.
		둘 이상이 읽거나 write-back 대상이 되는 데이터는 World ComponentDataStorage를 SSOT로 둔다.
		애매하면 공유 storage를 우선한다.
		OOP 즉시 반영과 System Apply가 같은 공유 컴포넌트를 동시에 쓰지 않도록 write-ownership을 phase 단위로 제한한다.

	7. 데이터 레이아웃 (compute / binding 분리)
		RuntimeEntry = System 소유 hot data(인라인) + 공유 storage로의 index.
		compute 패스는 인라인 hot data를 스트림하고, 공유 상태가 필요하면 index로 값만 읽는다. 관리(managed) 참조나 포인터 체인 추적은 하지 않는다.
		결과 반영(write-back)은 index로 World storage에 수행하며, 흩어진 write는 Apply 단계로 제한한다.
		저장이 연속이라고 접근이 연속인 것은 아니다.
		큰 System은 index 정렬·조밀화를 통해 접근 순서가 저장 순서와 가깝게 유지되도록 한다.

	8. 판정과 이벤트 (순서 의존 제거)
		같은 프레임의 상호작용 판정은 즉시 해결하지 않는다.
		1패스에서 이벤트/커맨드를 수집하고, 2패스에서 명시적 규칙으로 해결한다.
		판정 우선순위는 배열 순서가 아니라 문서화된 규칙으로 정한다.
		이벤트/커맨드 수집은 병렬 compute와 호환되도록 thread-local 또는 System-local buffer를 우선한다.

	9. 실행 순서 (Tick Phase)
		GameRuntime은 GlobalPreUpdate / ProcessBeforeWorldTicks / World Tick / ProcessAfterWorldTicks / GlobalFinalUpdate의 다섯 단계로 실행한다.
		Global은 프로세스 전역 싱글턴이 아니라 한 GameRuntime이 소유한 모든 World에 공통인 실행 범위다.
		각 World Tick은 PreUpdate / ProcessAll / FinalUpdate의 세 단계로 실행한다.
		PreUpdate와 FinalUpdate는 World-local OOP 실행 경계이고 ProcessAll은 World-local System 실행 경계다.
		현재는 단계와 호출 순서만 확정하며 Update 참여 목록, Scheduler, SystemSync / Compute / Resolve / Apply의 세부 분할은 후속 구현한다.
		후속 세부 phase를 추가하더라도 Runtime 다섯 단계와 World 세 단계의 상위 경계는 유지한다.

	10. 이번에 하지 않는 것
		DOTS식 기계장치(archetype chunk, Burst/SIMD, Job 자동 스케줄러)는 이번에 도입하지 않는다.
		지금은 developer-composed(명시적 enroll·Tick)로 두고, 자동 스케줄·병렬은 시스템 수·엔티티 수가 그 비용을 정당화할 때의 후속 과제로 남긴다.
		분기 압축(플래그화)·캐시라인 패킹은 엔트리 수가 큰 System에만 적용한다.
		GameObject와 Component의 Update 계약, 참여 의사, 활성 상태와 Scheduler 등록 정책은 #4_11에서 결정한다.

CyphenEngine_Runtime_World_Snapshot_Rule

*현재 #4 최소 구현에서 책임 경계를 검증하기 위한 선행 결정입니다.*
*Object/System/Physics 구현 결과에 따라 Snapshot의 데이터 구성, 보관 용량, 복원 정책, 네이밍은 변경될 가능성이 높습니다.*

	1. 책임과 실행 계층
		CyphenEngine은 프로세스 호스트이자 최상위 프레임 펌프다.
		GameRuntime은 하나의 실행 컨텍스트로서 World를 소유하고 World의 실행 여부, delta time 전달, snapshot 보관 정책을 조율한다.
		World는 Object와 System이 살아가는 하나의 논리 시뮬레이션 공간이자 현재 상태 컨테이너다.
		World::Tick은 자체 Run loop가 아니라 Runtime이 호출하는 한 번의 simulation step이다.
		실행 호출은 CyphenEngine::Run -> GameRuntime::Tick -> World::Tick 순서로 중첩된다.
		GameRuntime::Tick은 Runtime 다섯 단계를, World::Tick은 World 세 단계를 보장한다.
		따라서 Runtime 조율과 World::Tick은 대안 관계가 아니다. Runtime이 호출 정책을 소유하고 World가 자신의 상태 전진을 수행한다.

	2. 현재 최소 상태
		현재 World는 simulationTick, simulationTime, 원점 Chunk와 ComponentDataStorage<Transform, ObjectHandle>을 소유한다.
		World는 Join한 WorldObject의 비소유 참조를 유지하며 WorldObject의 메모리와 Object 수명은 소유하지 않는다.
		WorldObject는 생성 후 World에 Join하기 전까지 독립적으로 존재할 수 있다.
		Join은 WorldObject 참조와 Transform 정본을 연결하고 Leave는 이를 해제한다.
		ObjectManager는 ObjectHandle 발급, 활성 Registry, 지연 파괴를 담당하고 Object의 Outer/SubObject는 종속 수명만 표현한다.
		Update와 System 실행 참여 기계장치는 현재 구현하지 않는다.

	3. Live World, Snapshot, Render Frame
		World는 여러 tick에 걸쳐 유지되는 현재의 가변 simulation state다.
		WorldSnapshot은 특정 simulation tick으로 복구하기 위한 값 데이터다.
		Frame은 Renderer가 소비하는 표현 전용 입력이며 WorldSnapshot과 목적과 수명이 다르다.
		World는 WorldSnapshot을 capture/restore할 수 있지만 snapshot history 자체는 소유하지 않는다.

	4. Snapshot History
		GameRuntime은 초기 World 상태와 매 World::Tick 이후 상태를 고정 용량 원형 큐에 기록한다.
		현재 #4의 history 용량은 32개다.
		32개는 현재 경계와 원형 큐 동작을 검증하기 위한 초기값이며 실제 World 상태 크기와 목표 rollback 범위를 측정한 뒤 조정한다.
		0 ticksAgo는 가장 최근 snapshot이며 용량을 넘은 가장 오래된 snapshot은 덮어쓴다.
		과거 snapshot을 복원하면 기존 미래 history를 폐기하고 복원한 상태를 새 기준점으로 남긴다.
		60Hz 기준 32개 snapshot은 약 0.53초의 상태 범위다.

	5. Physics Snapshot 방향
		Physics가 추가되면 복구와 재시뮬레이션에 필요한 World-local persistent 상태를 WorldSnapshot에 포함한다.
		Body transform, velocity, sleep/activation, collider/constraint persistent state, World physics configuration은 포함 후보다.
		solver scratch memory, thread-local buffer, 재구축 가능한 broadphase cache, 일회성 contact buffer는 기본 제외 후보다.
		최종 포함 기준은 snapshot 복원 후 동일한 입력으로 시뮬레이션을 계속할 수 있는가이다.

	6. Rollback, Replay, Render Queue
		최근 snapshot history는 rollback/rewind의 상태 복구 기반이다.
		복원 이후 input 재실행, deterministic simulation 검증, network rollback은 후속 작업이다.
		장기 replay는 모든 full snapshot의 무기한 보관보다 초기 또는 주기적 keyframe snapshot과 input/event log 조합을 우선 검토한다.
		Render Frame Queue와 World Snapshot History는 데이터 목적, 용량, 수명 정책이 다르므로 통합하지 않는다.
		Rollback과 Replay는 현재 확정 기능이 아니라 Snapshot 구조가 열어 두는 미래 방향이며 실제 요구와 비용을 확인한 뒤 확정한다.

	7. Runtime과 World의 다중성
		현재 구현은 CyphenEngine 하나가 GameRuntime 하나를 구성하고, GameRuntime 하나가 World 하나를 소유한다.
		Editor MultiPlay를 위해 프로세스당 Runtime 0..N과 Runtime당 독립 World 가능성을 막지 않는다.
		Runtime과 World 상태는 전역/싱글턴으로 두지 않고 인스턴스 범위에 둔다.
		Runtime 컨테이너, EditorRuntime, PIE, 단일 프로세스/다중 프로세스 구성은 해당 기능 구현 시 결정한다.
