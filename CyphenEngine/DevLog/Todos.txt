## 현재 기준선

1. Core / Platform
	- Time, Path, File, FileSystem, TextCodec의 기본 경계는 정리된 상태입니다.
	- Core는 OS API를 직접 호출하지 않고, Platform 구현은 HAL 계약 뒤에 둡니다.
	- Windows / Linux 양쪽 PlatformFile, PlatformPath, PlatformTime, ModuleLoader 경로를 유지합니다.

2. Core Math
	- Mathf, Vector, Vector2D, Quaternion, Matrix4x4, Transform 기반의 3D-ready 월드 Math 계층을 유지합니다.
	- 기본 월드 좌표계는 왼손좌표계, +X 오른쪽, +Y 위쪽, +Z 앞쪽입니다.
	- #4 2D 월드는 XY 평면 제약으로 계산하고, Z는 깊이 / 레이어 / 정렬 값으로 사용합니다.
	- UI / 스크린 / UV 같은 진짜 2D 개념은 Vector2D를 사용합니다.

3. Renderer / Module
	- Renderer는 Renderer Module ABI를 통해 런타임 적재되는 선택 모듈로 구성합니다.
	- CyphenRendererDx11.dll은 Windows DX11 backend입니다.
	- CyphenRendererVulkan.dll / .so는 Windows에서 먼저 검증한 뒤 Linux X11 + Vulkan 실행까지 연결한 backend입니다.
	- CyphenRendererOpenGLES는 보류 슬롯으로 유지합니다.

4. Linux Porting
	- WSL2 / CMake / Ninja 기반 Linux 빌드 경로는 동작 확인된 상태입니다.
	- Linux GUI 실행에서 CoreIoTests PASS=69 FAIL=0, ModuleTests PASS=34 FAIL=0을 확인했습니다.
	- CyphenRendererVulkan.so 로드, Vulkan surface / swapchain / pipeline 초기화, 텍스처 출력까지 확인했습니다.


## 해야 할 일

1. 2D World
	- #4 브랜치의 우선 목표입니다.
	- debug fixture 수준의 텍스처 표시를 실제 2D 월드 표시 흐름으로 확장합니다.
	- Runtime / Editor 책임 경계를 다시 확인합니다.
	- 월드 데이터가 Frame / RenderCommand로 넘어가는 최소 경로를 설계합니다.

2. ResourceManager / FileSystem
	- Texture2D CPU decode와 GPU upload 경계를 ResourceCommand / RenderCommand 흐름 기준으로 유지합니다.
	- File이 제공하는 동기 I/O API를 ResourceManager / TaskSystem 계층에서 사용할 수 있도록 상위 로딩 구조를 검토합니다.
	- AssetId / ResourceHandle / PakHandle / Offset 기반 접근 구조를 검토합니다.
	- 런타임 hot path에서는 문자열 path 기반 반복 접근을 피하도록 설계합니다.
	- 파일 확장자 유형 기반 처리는 ResourceManager 또는 FileSystem 계층에서 검토합니다.

3. Mesh / Material
	- 2D 월드 표시를 위한 최소 Mesh 표현을 추가합니다.
	- Material은 renderer backend 세부 구현을 직접 노출하지 않는 방향으로 검토합니다.
	- Texture2D, Mesh, Material이 ResourceManager를 통해 묶이는 시점을 정합니다.

4. Renderer
	- Vulkan 출력의 상하좌우 반전은 좌표계 / UV 축 보정 문제로 보고 수정 여부를 판단합니다.
	- swapchain recreate / resize 대응을 별도 작업으로 정리합니다.
	- GPU device 선택과 validation layer 설정을 정리합니다.
	- renderer backend별 command decode 중복 정리 여부를 검토합니다.
	- Server / headless 빌드에서는 Renderer 모듈을 비활성화할 수 있어야 합니다.

5. Build Target / Runtime Config
	- BuildInfo를 CyphenEngine::Run 내부 BUILD_TARGET 분기에 실제 연결합니다.
	- Server / Editor / Windowed 타겟 구분을 Build 계층에서 명확히 합니다.
	- Renderer 모듈 활성화 여부를 빌드 설정과 실행 설정 양쪽에서 다룰 수 있도록 정리합니다.
	- RuntimeConfig는 렌더러 선택 / PIE / Standalone Play / Multiplay Mode 같은 런타임 옵션을 다룰 때 추가합니다.
	- Renderer 변경은 런처 재시작 또는 프로세스 재시작이 필요한 방향으로 둡니다.

6. Event / Window
	- WndProc -> PlatformEventQueue -> Engine Tick 소비 구조를 추가합니다.
	- Windows message loop와 Linux X11 event loop를 동일한 상위 이벤트 계약으로 올릴지 검토합니다.
	- NativeWindowInfo는 현재 windowed renderer 초기화를 위한 최소 전달 구조로 유지합니다.
	- Renderer 모듈 또는 별도 WindowSystem 계층이 platform window / surface를 직접 소유하는 구조가 확정되면 NativeWindowInfo 책임을 축소하거나 제거합니다.

7. Logger / Diagnostics
	- Windows는 OutputDebugStringA, Linux는 stderr 출력 경로를 기본 debug sink로 둡니다.
	- Fatal / Internal 계열 로그는 크래시 추적을 위해 즉시 출력 및 중단 처리 방향을 고려합니다.
	- 이후 Diagnostics 계층으로 LogRecord 생성과 큐 적재 책임을 분리할지 검토합니다.
